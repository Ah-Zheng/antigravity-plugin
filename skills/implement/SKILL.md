# Implement（規格落地實作協議）

> 「忠於規格，精準交付；拒絕加戲，安全優先。」
> 許多 AI 在實作時容易陷入三大陷阱：**過度設計（Gold-Plating）**、**重複發明既有輪子**、以及**破壞既有架構的一致性**。本協議要求：任何程式碼變更必須嚴格錨定在使用者提供的 PRD、Issue 或驗收條件（Definition of Done, DoD）上，以增量方式精確交付。

---

## 觸發時機

### 應主動啟動
- 使用者要求依據特定 PRD、功能規格書或 Issue 實作功能時
- 需要進行具備明確驗收準則（Acceptance Criteria）的特徵開發時
- 執行多步驟的中大型代碼重構或新模組接入時

### 無需啟動
- 單純的技術諮詢、架構討論或代碼概念解釋（請使用一般問答或規劃技能）
- 單一已知錯誤的緊急修復（可直接修復或搭配 `systematic-debugging`）

---

## 核心執行流程

```
[1. 範疇鎖定] ➔ [2. 現況取證] ➔ [3. 增量實作] ➔ [4. 驗收驗證]
  (明確 DoD)    (查明既有 Pattern)  (Typecheck)     (Diff & 自審)
```

### 步驟 1：範疇與驗收標準鎖定（Scope & DoD Freeze）
- **確認輸入邊界**：明確記錄本次任務的驗收條件清單（DoD）。
- **拒絕無端加戲**：嚴禁主動實作「未來可能會用到」、「順便加上」的額外功能或未要求的抽象層。
- 若需求存在模糊地帶，主動向使用者提出最小化釐清，不逕自通靈推演。

### 步驟 2：現況取證與依賴對齊（Align with Codebase）
- 在編寫任何新檔案前，必須確認：
  1. 專案中是否已有類似功能的實作？（優先調用 `wiki-qa` 取證）
  2. 現有的型別定義、API 封裝、UI 元件庫為何？
  3. 檔案架構是否遵循既有規範（如 FSD、模組化邊界、命名慣例）？
- **絕對禁止**在專案已有共用工具函式的情況下重新自行造輪子。

### 步驟 3：增量實作與即時檢查（Incremental Implementation）
- **垂直切片推進**：依功能層次小步推進（例如：定義型別 ➔ 實作資料層 ➔ 串接邏輯 ➔ 實作 UI）。
- **即時靜態分析**：
  - 每次完成一處修改，必須確認型別檢查通過（如 TypeScript 無型別報錯）。
  - 維護程式碼的完整性，不留下未實現的空 stub 或 `TODO` 爛攤子。

### 步驟 4：交付驗證與自審查檢（Verification & Self-Review）
- **逐條核對 DoD**：逐一驗證步驟 1 列出的驗收標準是否全部滿足。
- **Diff 自審**：檢視變更差異，確保沒有多餘檔案或非預期的副作用修改。
- **提供清晰變更清單**：向使用者說明修改了哪些檔案、實現了什麼能力、以及後續如何驗證。

## 資安防護與邊界（Security Safeguards）

實作代碼時必須嚴格把守以下安全防禦，消除常見漏洞與非授權操作：

1. **嚴禁自動 Git 操作（No Unauthorized Git State Mutation）**：
   - ⚠️ 原版規則中盲目的 `Commit your work to current branch` 存在嚴重安全隱患！
   - **修正方針**：AI 實作完成後，**絕對禁止**在未經使用者授權與檢閱前自動執行 `git commit` 或 `git push`。所有版本控制提交必須由使用者親自檢視 Diff 確認無誤後指示執行。
2. **供應鏈安全與依賴引進防禦（Supply Chain Protection）**：
   - 嚴禁未經確認自行執行 `npm install <package>`、`pip install` 等引入全新第三方依賴。
   - 優先使用專案現有依賴；若必須新增套件，必須先說明套件名稱、版本、用途與安全理由，取得使用者許可後方可安裝。
3. **安全編碼防線（Secure Coding Standards）**：
   - **防注入**：所有外部輸入必須驗證與消毒，嚴禁拼接未經處理的 SQL 語句、Shell 指令或未經轉義的 HTML 輸出（防範 XSS / SQLi / Command Injection）。
   - **禁止硬編碼憑證**：嚴禁在代碼中寫死密碼、API Key、Token 或內部連線字串。一律透過專案設定的環境變數機制讀取。
   - **最小檔案異動原則**：禁止為了改動一行代碼而格式化整份無關的檔案，避免污染 Git History 與干擾程式碼審核。

---

## 鐵則（Iron Rules）

1. **DoD 為唯一完成判準**：代碼寫完不算完成，通過驗收標準才是完成。
2. **禁止擅自提交 Git**：完成實作後僅呈現具體變更，提交權限保留給使用者。
3. **尊重專案既有規範**：寫出的程式碼必須看起來像是同一個團隊、同一套 Coding Style 寫出來的。
