# TDD（測試驅動開發規範）

> 「測試即規格；行為重於細節，綠燈方得重構。」
> 測試驅動開發的核心目的不是為了「提高測試覆蓋率數字」，而是為了**將需求具象化為精確的行為契約（Behavior Contract）**。藉由先寫測試，迫使設計聚焦在公開 API 與使用者意圖上，杜絕憑空想像多餘代碼。

---

## 核心設計哲學

### 1. 驗證行為，而非實作細節（Behavior, Not Implementation）
- **優良測試**：透過模組的**公開介面（Public APIs）**驗證其對外行為。
  - 測試案例應讀起來像業務規格（例如：`it("使用者購物車具備有效商品時應成功結帳")`）。
  - 當內部重構（如變更私有函式名稱、調整內部演算法）時，只要行為不變，**測試絕對不應崩潰**。
- **劣質測試（反模式）**：與內部實作深度耦合。
  - 過度 Mock 內部輔助函式、測試私有方法、或繞過公開介面直接查庫驗證。
  - 一旦重構內部結構，測試就大面積壞死，徒增維護負擔。

### 2. 嚴禁水平切片反模式（No Horizontal Slicing）
- ❌ **絕對禁止**一次寫完 10 個測試，然後才開始寫程式碼（這會導致憑空想像規格、測試脫離真實反饋）。
- ✅ **堅持垂直切片（Vertical Slices / Tracer Bullets）**：
  ```
  一個具體測試 ➔ 一段剛好通過的最小程式碼 ➔ 重構 ➔ 重複下一個測試
  ```

## 執行流程（Red-Green-Refactor 循環）

```
   ┌────────────────────────────────────────┐
   ▼                                        │
[ 1. RED (紅燈) ]  ➔  [ 2. GREEN (綠燈) ]  ➔  [ 3. REFACTOR (重構) ]
  寫一個失敗測試        寫出最小必要程式碼        在綠燈保護下清理壞味道
```

### 階段一：RED（紅燈）
1. 依據需求，針對**單一具體行為**撰寫一個測試案例。
2. 執行該測試，**確認它必定失敗**，且失敗的原因必須是「功能尚未實作」，而不是測試本身的語法錯誤或 Import 遺失。

### 階段二：GREEN（綠燈）
1. 撰寫**剛好能讓該測試通過的最小必要程式碼**。
2. 甚至可以先使用硬編碼（Hardcoded value）或最簡單的邏輯，只要能讓測試變綠即可。
3. 嚴禁在綠燈階段預先撰寫尚未被測試覆蓋的額外邏輯。

### 階段三：REFACTOR（重構）
1. 在測試全綠的安全保護網下，檢視並優化程式碼：
   - 消除重複代碼（DRY）。
   - 改善命名與模組職責劃分。
   - 提取共用邏輯或常數。
2. 重構過程中**反覆執行測試**，確保每一次小改動依然維持綠燈狀態。

## 資安防護與邊界（Security Safeguards）

測試通常具備執行任意代碼的權限，必須建立嚴密的資安隔離措施：

1. **嚴禁測試環境副作用（No Destructive Side Effects）**：
   - 測試程式碼**絕對禁止**連線到任何真實的外部生產/測試環境、第三方 API 或正式資料庫。
   - 所有外部依賴（網路請求、檔案系統寫入、金流服務）必須使用 Mock 或隔離的記憶體資料庫（In-memory SQLite / Mock Server）。
   - 避免測試執行導致資料被污染、被覆寫或產生未預期的外部費用。
2. **禁止在測試資料中使用真實敏感資訊（No Real PII / Secrets in Fixtures）**：
   - 測試 Fixture、Mock 物件或快照（Snapshots）中，**嚴禁**出現真實使用者的個人可識別資訊（姓名、電話、真實身分證、真實 Email）或實際金鑰密碼。
   - 一律使用虛擬合成資料（Dummy data，如 `test-user@example.com`、`dummy_token_123`）。
3. **安全邊界測試覆蓋（Security Edge-Cases Testing）**：
   - 在設計測試案例時，除了正常路徑（Happy Path），必須主動加入安全邊界行為：
     - 超長字串輸入（Buffer / Memory bounds）
     - 特殊符號與注入字串（`' OR 1=1 --`, `<script>`）
     - 未授權 / 過期 Token 之拒絕存取測試

## 鐵則（Iron Rules）

1. **沒看到紅燈不寫代碼**：未有明確失敗測試前，禁止提前實作功能。
2. **只寫最小代碼**：綠燈階段不求完美，但求通過；多餘的程式碼就是未來的 Bug。
3. **測試與內部實作解耦**：重構內部邏輯時若需修改測試簽名，必須警惕是否測到了實作細節。
