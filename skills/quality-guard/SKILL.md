# Quality Guard（自適應產出品質守護門禁）

> 「交付之前，先行自省；代碼求潔，文檔求真。」
> 本協議為產出物展示給使用者前的**最後一道防護門禁（Pre-delivery Gate）**。無論 AI 剛才撰寫的是生產程式碼還是技術文件，皆強制在背景自動執行對應的自檢清單，**自己發現缺陷、自己默默修好**，杜絕粗製濫造、廣義吞報錯、寫死假數據或虛構 API。

---

## 觸發時機

### 應主動啟動
- 剛完成功能實作、修復 Bug 或重構程式碼，準備交付給使用者前
- 剛使用 `wiki-onboarding` 或其他工具產出技術文檔、架構全景圖、API 指南或 README 後
- 使用者要求「幫我做產出品質檢查」或明確輸入 `/quality-guard` 時

### 無需啟動
- 單純的概念問答、聊天討論或搜尋檔案時

---

## 自適應檢查機制（雙軌自檢）

依據本次產出內容的屬性，AI 必須在背景強制切換對應軌道執行自檢：

```text
                               【 /quality-guard 守護門禁 】
                                         │
                 ┌───────────────────────┴───────────────────────┐
                 ▼                                               ▼
      【軌道 A：代碼產出自檢】                         【軌道 B：技術文檔自檢】
      (針對程式碼檔案與 Diff)                        (針對 Markdown、導覽、註解)
```

---

### 軌道 A：代碼產出自我檢查（Code Guard Pass）

在將程式碼呈現給使用者前，逐一核對以下鐵則：

1. **命名與函式邊界**：
   - 函式長度目標 ≤ 20 行，職責單一。
   - 參數數量 ≤ 4 個（超過需重構為 Config / DTO 物件）。
   - 拒絕無意義命名（如 `temp`, `data2`, `obj`, `handle_stuff`）。
2. **防範 LLM 典型不良習慣（高槓桿檢查）**：
   - 🚫 **嚴禁廣義吞錯誤（No Broad Catch-all）**：禁止使用空的 `catch (e) {}` 或直接回傳 null/空物件。必須指定精確 Error Type 或讓其正常冒泡。
   - 🚫 **嚴禁寫死假資料（No Hardcoded Mocks in Production）**：嚴禁在真實函式中回傳 `{"status": "ok"}` 假裝成功。無法實作者必須明確拋出未實現例外。
   - 🚫 **嚴禁未驗證外部調用**：調用第三方庫時，必須確認專案現行版本確實存在該方法，嚴禁憑記憶想像 API。
3. **代碼潔淨與精簡**：
   - 註解只解釋「為什麼（Why）」，絕不翻譯「程式碼在做什麼（What）」。
   - 交付前徹底清除無用的死代碼、未使用的 Import 與暫存 `console.log`。

---

### 軌道 B：技術文檔自我檢查（Docs Guard Pass）

在將技術文件、架構導覽交付給使用者前，逐一核對以下鐵則：

1. **符號與路徑真實存在性（Symbol Verification）**：
   - 文件中提及的函式、Class、CLI 指令、環境變數名稱與檔案路徑，**必須在專案源碼中實際查證存在**。
   - 查不到、不確定的符號絕對不准寫進文件。
2. **範例代碼真實可執行（Runnable Code Samples）**：
   - 示範代碼的 Import 路徑、參數順序與回傳格式必須與目前原始碼 100% 吻合。
   - 範例嚴禁包含開發者本機硬編碼絕對路徑或真實金鑰。
3. **記述現狀而非願景（Actual Behavior, Not Wishful Thinking）**：
   - 嚴格記錄程式碼當前真實運作的邏輯，禁止將程式碼中的 `TODO` 或未來規劃當成現有功能。
4. **剔除無法驗證的行銷吹噓**：
   - 刪除「效能極致」、「超高可用」等空洞形容詞，替換為具備測試或行號佐證的事實。
5. **Mermaid 圖表語法防禦自檢（Mermaid Syntax Safety）**：
   - 凡產出文件包含 `mermaid` 程式碼區塊，交付前必須自檢修復：
     - 檢查所有含括號 `()`、方括號 `[]` 或特殊符號的節點，是否均以雙引號包裹（`id["..."]`）。
     - 檢查是否誤用關鍵字（如 `end`）作為節點 ID（若有，自動修正為 `node_end`）。
     - 檢查 `subgraph` 是否皆為標準格式 `subgraph ID ["名稱"] ... end`。
     - 檢查連線文字是否符合 `-->|"標籤"|` 格式。
     - 發現任何語法隱患，必須**原地自動修復修正**後才交付。

---

## 自檢結果回報規範

當自檢與背景修復完成後，在回覆的最後附帶簡明的一行報告，讓使用者知悉門禁已通過：

* **完全無違規時**：
  `quality-guard: clean`
* **有自我修復時**：
  `quality-guard: <N> 項已自動修復，<M> 項提醒作者關注`
  *(並條列修復了哪些檔案與項目)*

---

## 鐵則（Iron Rules）

1. **自檢不過不交付**：只要自檢清單中有違規，AI 必須在內部修改後才准送出回覆。
2. **真實為本**：代碼拒絕假 mock，文檔拒絕通靈 API。
3. **靜默自修**：小缺陷（格式、命名、死代碼、路徑錯）自行修正，不浪費對話輪次向使用者頻繁詢問。
