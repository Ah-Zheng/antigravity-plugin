# Review and Simplify Changes（代碼精簡與複用審查協議）

> 「刪除多餘代碼，善用既有輪子；精準重構，行為守恆。」
> 許多代碼變更在功能完成之餘，常伴隨著**「重複造輪子（忽略既有工具函式）」**、**「不必要的冗餘狀態」**、以及**「過度巢狀的複雜邏輯」**。本協議專門針對 Git Diff 進行代碼複用與簡潔度審核，並可在明確授權下，執行**保持既有行為 100% 不變**的安全精簡。

---

## 觸發時機

### 應主動啟動
- 使用者要求「幫我看看這段 diff 有沒有寫得太囉嗦/能不能精簡？」
- 檢查代碼變更中是否有「重複發明現有專案已有之輪子」的情況
- 在確認功能正常後，進行提交前的代碼清潔與重構審視

### 無需啟動
- 尚未釐清業務邏輯的階段
- 需要大刀闊斧變更系統架構（此時請使用架構規劃技能）

---

## 支援模式

AI 必須依據使用者指令明確判定運作模式，**預設為唯讀審查**：

1. **`review-only`（預設模式）**：
   - 當指令為「審查」、「檢查」、「Review」時啟動。
   - **純唯讀**，只產出問題清單與建議改法，不改動任何檔案。
2. **`safe-fixes`（安全修復模式）**：
   - 當使用者明確表示「幫我精簡」、「幫我清理」、「重構這段修改」時啟動。
   - 僅針對**高信心、100% 保持行為一致**的項目進行局部代碼簡化。
3. **`fix-and-validate`（修復並驗證模式）**：
   - 完成安全精簡後，自動執行最小範圍的型別檢查（Typecheck）或單元測試驗證改動。

## 四大審查與精簡焦點

```text
┌──────────────────────────────────────────────────────────────┐
│             [ REVIEW & SIMPLIFY 四大精簡焦點 ]               │
├──────────────────────────────┬───────────────────────────────┤
│ 1. 代碼複用 (Code Reuse)     │ 2. 代碼純度 (Code Quality)    │
│    - 既有 Helper/Util 忽視    │    - 冗餘 State / 衍生值多餘儲存 │
│    - 複製貼上微改 (重複輪子)  │    - 參數蔓延 (Parameter Sprawl)│
├──────────────────────────────┼───────────────────────────────┤
│ 3. 執行效率 (Efficiency)     │ 4. 可讀規範 (Clarity & Rules) │
│    - 重複計算 / 多餘 I/O      │    - 死代碼 (Dead Code) / 無用抽象│
│    - 巢狀過深 (箭頭代碼)      │    - 符合專案專屬代碼風格慣例  │
└──────────────────────────────┴───────────────────────────────┘
```

1. **代碼複用（Code Reuse）**：
   - 專案內部是否早已有封裝好的共用函式、Hook 或 UI 元件？
   - 是否出現「同一個格式化邏輯在兩處各寫一次」的情況？
2. **代碼質量（Code Quality）**：
   - 是否儲存了可以透過計算直接取得的冗餘狀態（Derived State）？
   - 函式參數是否層層傳遞（Props Drilling）而導致簽名膨脹？
3. **執行效率（Efficiency）**：
   - 是否在迴圈或熱門呼叫路徑上重複解析資料或重複打 API？
   - 是否有可以提早 Return（Guard Clause）的深層巢狀邏輯？
4. **清晰度與死代碼（Clarity & Dead Code）**：
   - 修改後是否遺留了不再被引用的變數、函式或 Import？
   - 是否存在為了炫技而寫的難懂簡寫？

## 安全精簡規則（若進入 safe-fixes 模式）

當獲得授權修改代碼時，必須嚴格遵守以下安全防線：

- **行為守恆定理**：所有重構必須保證輸入與輸出的外部行為完全不變。
- **拒絕主觀美學變更**：不得僅僅因為「這樣排版比較好看」而大面積修改無關代碼。
- **優先使用現有函式庫**：將手寫的輔助邏輯替換為專案現成的工具函式。
- **嚴禁擴大檔案範疇**：修改僅限於 Diff 涉及的檔案，禁止順手修改整個目錄。

---

## 資安防護與邊界（Security Safeguards）

1. **嚴禁自動版本控制操作**：
   - 就算代碼精簡完成，**絕對禁止**自動執行 `git commit` 或 `git push`。最終審閱與 Commit 權利永遠屬於使用者。
2. **命令執行沙盒化（防 Command Injection）**：
   - 在 `fix-and-validate` 模式中，僅調用專案現成安全的驗證指令（如 `npm run typecheck`、`npm test <特定檔案>`），絕不執行任何外部未知指令。
3. **防止過度簡化導致的安全漏洞**：
   - 嚴禁為了「精簡行數」而移除必要的輸入防禦、型別防衛或錯誤捕獲（Error Handling）。

---

## 鐵則（Iron Rules）

1. **未經指示不改代碼**：預設為唯讀審查，只有使用者要求時才能動手精簡。
2. **不確定的代碼不動**：若精簡可能牽動隱性業務邏輯，僅提出建議，絕不自行下定論。
3. **完成後驗收差異**：若進行了精簡，必須清楚條列：「修改了什麼、保留了什麼、省去了什麼」。
